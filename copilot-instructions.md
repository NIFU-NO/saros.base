# Copilot Instructions for saros.base

## Testing Workflow

Immediately alert the user if there exist no tests for the given
functions they are working on.

### Quick Testing (Preferred)

Use this for faster iteration during development:

``` r
devtools::load_all(); devtools::test()
```

- **Faster** than full check
- Runs all tests
- Good for verifying code changes quickly

### Full Package Check

Only use when necessary (e.g., before PR):

``` r
devtools::check()
```

- **Comprehensive** but slower
- Includes documentation checks, examples, etc.
- No need to run `load_all()` and `test()` separately when using this

**Important:** Never run both `devtools::check()` AND
`devtools::load_all(); devtools::test()` together - `check()` already
includes testing.

## Git Workflow Commands

### “git” command

When user says “git”: 1. Check git status 2. If on main branch with
changes, create a new branch first 3. Create commits grouped by logical
features/bug fixes 4. Tests and documentation should be grouped with the
code they relate to

### “PR” command

When user says “PR”: 1. Push the current branch to GitHub 2. Create a
Pull Request

### “PR merged” command

When user says “PR merged”: 1. User has already merged PR manually on
GitHub 2. Switch to main branch 3. Pull latest changes 4. Delete local
branch 5. Delete remote branch 6. Clean up

## R Development Commands

When working with this R package, use these command formats:

### Documentation Generation

``` powershell
Rscript.exe -e "devtools::document()"
```

### Running Tests (follow Testing Workflow above)

``` powershell
# Quick testing (preferred for development)
Rscript.exe -e "devtools::load_all(); devtools::test()"

# Full check (use before PR, includes tests)
Rscript.exe -e "devtools::check()"
```

## File Patterns to Ignore

- `copilot-analysis-*.md` - Analysis files generated by Copilot
- `air.toml` - Build tool configuration

## Test Failure Extraction

When running `devtools::test()`, immediately extract and analyze
failures:

1.  **Look for failure markers**: `FAIL`, `Error`, `Failure`
2.  **Extract context**: Include the test file name, line number, and
    failure message
3.  **Identify patterns**: Group similar failures together
4.  **Report concisely**: Summarize unique failure types without
    repeating full output

### Example Failure Extraction Pattern

From test output:

    ✖ | 3       12 | shared-instruments
    ─────────────────────────────────────────────────
    Failure (test-shared-instruments.R:36:3): resolve_instrument_config merges with config
    Expected `result$regex` to equal "^([a-z]+)".

Extract as: - **File**: test-shared-instruments.R:36 - **Test**:
resolve_instrument_config merges with config - **Issue**: `result$regex`
expected `"^([a-z]+)"` but got `NULL`

## Command Auto-Approval

These commands are pre-approved in `.vscode/settings.json` and do not
require user confirmation.

## Response Efficiency

- **Don’t announce** which tool you’re using
- **Don’t create** summary markdown files unless requested
- **Do provide** clear, actionable next steps when failures occur
